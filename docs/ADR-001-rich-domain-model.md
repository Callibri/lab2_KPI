# ADR-001: Rich Domain Model замість Anemic

- **Статус:** прийнято
- **Контекст:** у лабі 1 бізнес-правила (бюджет > 0, дата звіту не в майбутньому й не раніше прем'єри, формат email) були функціями в `validators.py`, які викликались із роутерів. ORM-моделі були «порожніми» рядками таблиць. Для лаби 2 потрібно обрати Anemic чи Rich Domain Model.
- **Рішення:** Rich Domain Model.
  - `Movie`, `BoxOfficeReport`, `User` — сутності з поведінкою (`Movie.update`, `Movie.ensure_accepts_report_for`, `BoxOfficeReport.correct`) і перевіркою інваріантів у `__post_init__`.
  - `Email`, `Money`, `RegionCode` — Value Objects, які неможливо створити в невалідному стані.
  - Створення об'єктів, що потребують БД (унікальність), — у фабриках `UserFactory`, `MovieFactory`, `ReportFactory`.
- **Обґрунтування:**
  1. Інваріанти лежать поруч з даними — невалідну сутність створити неможливо, на відміну від лаби 1, де достатньо було обійти валідатор.
  2. Домен тестується без БД і фреймворку (`tests/domain`).
  3. Правила предметної області (ROI, перевірка дати звіту) мають одне місце, а не копіюються між роутерами.
- **Наслідки:** більше коду (мапери ORM↔домен, окремі DTO), доменні об'єкти потрібно відновлювати з БД через мапери. Прийнятна ціна за захищені інваріанти.
- **Розглянуті альтернативи:** Anemic Model + сервісний шар — простіше, але правила розтікаються по сервісах і легко порушуються.
